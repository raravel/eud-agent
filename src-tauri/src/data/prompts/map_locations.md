[map regions and location budget]
- Apply this policy to every game, skill and map task. Ordinary area references do not request CHK locations. Save named gameplay areas as target selections through map_selection_write and read exact geometry with map_selection_list/map_selection_read. A selection consumes no location slot and grants no extra write authority.
- Prefer coordinate data for placement rows/cells, arena bounds, spawn points, route waypoints, management zones and leak checks. Preserve unions and exclusions for nonrectangular areas; do not silently replace an exact mask with its bounding rectangle. Verify edge inclusion and unit collision semantics when replacing location-based conditions with coordinate checks.
- Selections are authoring metadata, not a StarCraft runtime API. Bind verified saved geometry into the owning EPS/Python module as coordinates, waypoint arrays or masks; convert tile coordinates to map pixels deliberately (32 pixels per tile). Re-read after map changes/Apply and update affected runtime data and player bindings before building. Prefer tracked units and maintained state over scanning every unit for every region each tick.
- When a verified API needs a location, prefer a small project-owned runtime location pool: acquire distinct slots, set their coordinates/required flags immediately before the consuming action or condition, execute, then release on every path. An API needing a location does not itself justify one permanent location per row, waypoint, unit or player.
- Size the pool for the maximum simultaneously live uses, including source/destination pairs and nested calls, not the total areas or players. Sequential synchronized player processing may reuse slots. Record slot ownership, call lifetime and a deterministic exhaustion policy; never steal an active slot. Do not release while a deferred action or another trigger still depends on its bounds; retain ownership or use a dedicated location when its lifetime requires one. Keep acquisition, coordinate changes and consuming gameplay actions synchronized, outside local-only UI branches.
- Before reserving pool slots or creating a dedicated location, inspect existing locations, source references and installed helper/plugin usage. Reuse only explicitly owned pool slots; never take an apparently empty slot, an existing gameplay location or a helper's slot without establishing ownership. Keep numeric ids stable, exclude #64 Anywhere, and budget against the actual map capacity (up to 255 slots, fewer on original-SC maps).
- Use dedicated fixed locations when the user explicitly requests location creation/editing or exact map.location use, or when persistent trigger/API semantics require stable bounds that the pool cannot preserve. Read locations before binding ids/names. Reuse exact name/bounds for fixed regions; create only justified missing slots through the supported journaled location-write/candidate workflow. Resolve conflicting names/bounds with the user rather than overwriting, renaming or silently suffixing them. Never create a duplicate for an exact map.location mention.
- Document the purpose of each dedicated location and the pool's peak live-slot requirement in the design spec. A general area request or map.region mention alone must not produce location.add/location_write(add). Never create, delete or repurpose #64 Anywhere, automatically expand map capacity, or delete existing locations merely to meet the budget. Trace all references before an authorized migration.
- Verify the installed EPS/Python equivalent of pool coordinate-setting and consuming APIs with project code or search_docs/docs_get before implementation; do not invent a pool API or memory offset. Map Agent authors requested geometry and justified location slots through its candidate tools; EPS owns runtime pool logic and builds it. Use only tools advertised in the current session.
