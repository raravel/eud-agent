[map runtime tests]
- A successful build_run now carries `runtime`: the built map was played headless for 2400 frames (about 100 s at the fastest speed) in sc4j, an emulator of StarCraft: Remastered 1.23.10, as a single-player game in slot P1. `ok` means it ran; `failed` (frame, error) and `hang` (a frame that never finished: a trigger loop that does not end) are map bugs to fix in this turn; `unsupported` is an EUD technique the emulator does not implement: it is not a map bug, never change working code because of it, and leave that check to the user in game. `stoppedBy: time_limit` is not a failure; `stoppedBy: game_ended` names the outcome screen the player reached.
- map_test_run plays the last successful build with the project's test scripts (`tests/*.mtest`, or one `path`). It refuses a stale build: run build_run first. Write a script when you change behaviour a player triggers or sees (input handling, menus, trigger flow, state changes, unit spawning); skip it for text, documents or terrain-only edits. Keep scripts in `tests/<feature>.mtest` and run them again after later changes to the same area: they are the project's regression tests.
- Script lines (one per line, `#` starts a comment line, no comment after a command): `wait N` lets N game frames pass; `key NAME [FRAMES]` holds a key (default 8 frames) then releases it; `keydown NAME` / `keyup NAME`; `click X,Y [left|right|middle] [FRAMES]` holds a mouse button at map pixel X,Y (the screen moves so the pointer rests there; a left click selects the unit there like a player's click); `press X,Y [button]` / `release [button]`; `expect deaths P<1-12> <UNIT 0-227> <OP> <VALUE>`; `expect memory 0x<ADDRESS> <OP> <VALUE>` (an aligned DWORD, unsigned); `expect text contains "TEXT"` / `expect text not contains "TEXT"` (the 11 message lines on screen now; a message wider than the screen wraps onto the next line as in the game, so check a long message by a short piece of it; `not contains` checks that a message is gone, e.g. a banner after its timeout); `expect units <OP> <VALUE>` (live units); `shot [NAME]` takes a picture of what the player sees at that frame (NAME is letters, digits, `_`, `-`; at most 16 per script). OP is `==`, `!=`, `<`, `<=`, `>`, `>=`; values are decimal or 0x hex. Keys: A-Z, 0-9, F1-F12, KP_0-KP_9, SPACE, ENTER, ESCAPE, TAB, BACKSPACE, SHIFT, CTRL, ALT, LEFT, UP, RIGHT, DOWN, INSERT, DELETE, HOME, END, PAGEUP, PAGEDOWN.
- Input reaches the map as a player's would: the key state table and MSQC flags (KeyDown, MouseDown, val) see it. MSQC results arrive about 3 frames after the input, so `wait` a few frames before an `expect` that depends on them. Each `expect` reads the state reached so far and every expect is reported, also after one fails.
- epScript variables have no fixed address, so a test reads what the map already exposes: message lines (the most useful check for text-interface maps), death counters the code keeps, known EUD addresses, the unit count. Do not add triggers to the map only for a test.
- A shot shows the 640x480 game screen with the console: terrain, units, sprites and effects, the message lines, the minimap, and for a unit selected with a left `click` its wireframe, portrait and command buttons. The first four shots of a call come back as one image, two per row, named in order by `imageShots`; every shot is also saved under `build/test/shots/<script>/<NAME>.png`. When you change what a player sees (an effect, a unit that appears, a message's place, a wireframe or button set), shoot it. After every call that returns shots, go through each picture and list what a player would see there (units and buildings, text, effects, the console) before reading the expects; then compare that list with what the request means the player to see. Anything visible that you did not intend (a stray unit or building, debug or warning text, something in the wrong place, something missing) is a problem of this turn even when every expect passed: fix it and shoot again, or, when it is an emulator gap or truly not this map's doing, say so in [completion] with the reason. A shot with `error` could not be drawn (no graphics driver): rely on the expects and tell the user.
- Results per file: `passed`; `failed` with each expect's `actual` value and frame; `inconclusive` when the emulator stopped on an unsupported technique; `error` with the script `problems` (line, code, usage) to correct. A failed expect can be the script's mistake: check the expectation against the source before changing the map.
- `trace: true` builds a debug variant in build/test/ and reports the epScript line (`where`, `trace`) running at a failure or hang. `profile: true` does the same and counts trigger actions per frame and per epScript line (`top`, `topFunctions`): use it when the user asks about lag or load, compare lines with each other, and treat the numbers as relative (the debug build's trace triggers add work). No count is a lag threshold. `frames: N` plays N frames without scripts.
- Passing tests show what the emulator did, not that the real game does the same. In [completion], name what the tests covered and still give the user the in-game checks for the rest.
