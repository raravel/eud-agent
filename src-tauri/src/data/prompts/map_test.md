[map runtime tests]
- A successful build_run now carries `runtime`: the built map was played headless for 2400 frames (about 100 s at the fastest speed) in sc4j, an emulator of StarCraft: Remastered 1.23.10, as a single-player game in slot P1. `ok` means it ran; `failed` (frame, error) and `hang` (a frame that never finished: a trigger loop that does not end) are map bugs to fix in this turn; `unsupported` is an EUD technique the emulator does not implement: it is not a map bug, never change working code because of it, and leave that check to the user in game. `stoppedBy: time_limit` is not a failure; `stoppedBy: game_ended` names the outcome screen the player reached.
- map_test_run plays the last successful build with the project's tests (`tests/*.test.js` and older `tests/*.mtest`, or one `path`). It refuses a stale build: run build_run first. Write a test when you change behaviour a player triggers or sees (input handling, menus, trigger flow, state changes, unit spawning); skip it for text, documents or terrain-only edits. Keep tests in `tests/<feature>.test.js` and run them again after later changes to the same area: they are the project's regression tests. Write new tests in JavaScript only; leave an existing `.mtest` as it is unless you change that test.
- A test file is JavaScript for Rhino 1.8.1: `let`/`const`, arrow functions, template strings and `function*` work; `class`, `async`/`await`, spread `...`, `import`/`export`, `Date`, `eval` and timers do not. A `const` inside a loop keeps its first value in Rhino: use `let` there. The file declares `function* test(t)`, which starts after the game's first frame. Everything it does between two `yield`s happens at once on the state reached so far; frames pass only at a `yield`:
  - `yield t.wait(N)` lets N game frames pass. `const frames = yield t.until(() => CONDITION, MAX)` waits frame by frame until the condition holds and gives the frames waited; after MAX frames without it the test fails and ends.
  - `yield t.key(NAME, FRAMES = 8)` holds a key, then releases it; `t.keyDown(NAME)` / `t.keyUp(NAME)`. Keys: 'A'-'Z', '0'-'9', 'F1'-'F12', 'KP_0'-'KP_9', 'SPACE', 'ENTER', 'ESCAPE', 'TAB', 'BACKSPACE', 'SHIFT', 'CTRL', 'ALT', 'LEFT', 'UP', 'RIGHT', 'DOWN', 'INSERT', 'DELETE', 'HOME', 'END', 'PAGEUP', 'PAGEDOWN'.
  - `yield t.click(X, Y, BUTTON = 'left', FRAMES = 8)` holds a mouse button at map pixel X,Y (the screen moves so the pointer rests there; a left click selects the unit there like a player's click); `t.press(X, Y, BUTTON)` / `t.release(BUTTON)`; `t.view(X, Y)` centres the screen on a map pixel without clicking or selecting (use it to aim a shot). `t.chat(TEXT)` enters a chat line as the player (the runner then plays that test as a one-player network game, where the chat box writes the line).
  - Reads: `t.text()` (the 11 message lines on screen now, an array of strings; a message wider than the screen wraps onto the next line as in the game, so check a long message by a short piece of it), `t.deaths(PLAYER 1-12, UNIT 0-227)`, `t.memory(ADDRESS)` (an aligned DWORD, unsigned), `t.units()` (live units), `t.frame()` (frames played).
  - Checks: `t.expect(VALUE)` followed by `.toBe(X)`, `.not.toBe(X)`, `.atLeast(N)`, `.atMost(N)`, `.above(N)`, `.below(N)`, `.toContain(TEXT)`, `.not.toContain(TEXT)` (on `t.text()`: some line contains it, or none does, e.g. a banner gone after its timeout). Every check is reported with its line, `actual` value and frame, also after one fails, and returns whether it held. `t.require(VALUE)` takes the same matchers and ends the test when it fails: use it where the rest of the test means nothing without it.
  - `t.shot(NAME)` takes a picture of what the player sees now (NAME is letters, digits, `_`, `-`; at most 16 per test).
  - `t` works only inside `test(t)` and `t.until` conditions, never in a hook.
- The SC:R Enhanced game API is there as in a map script, so a test can set up the situation it checks instead of playing up to it: `game.players.get(0)` is P1 (ids are 0-based, unlike `t.deaths`); a player has `getMinerals()`, `setMinerals(n)`, `getGas()`, `setGas(n)`, `getStartLocation()`; `game.units.create(UnitType.TerranMarine, player, position)` places a unit as the Create Unit action does and returns `null` where none fits (`UnitType.get(id)` takes a unit id, `Position.of(x, y)` a map pixel); `game.units.find({type, owner})`, `count(...)`, `findInRadius(position, radius)`; a unit has `getHp()`, `setHp(n)`, `damage(n, player)`, `kill(player)`, `exists()`, `getPosition()`, `getOwner()`; `game.switches.isSet(i)`/`set(i, on)`; `game.print(text)`; `log.info(...)` writes to the result's `jsLog`. Hooks are top-level functions such as `function onUnitDied(event)` (`event.getUnit()`, `getKillerPlayer()`), `onUnitDamaged` (`getAmount()`), `onUnitCreated`, `onFrame(frame)`; they run each frame before the triggers. Set up only what the check needs and never use the API to do the map's own job (spawning the wave the triggers should spawn, writing the value the code should write): the test then proves nothing.
- Example:
  ```js
  // tests/q_skill.test.js: Q casts the hero's skill on the zerglings around it
  function* test(t) {
      const p1 = game.players.get(0);
      const hero = game.units.find({type: UnitType.HeroJimRaynorMarine, owner: p1})[0];
      t.require(hero !== undefined).toBe(true);
      const at = hero.getPosition();
      for (let i = 0; i < 3; i++) game.units.create(UnitType.ZergZergling, game.players.get(7), Position.of(at.getX() + 64, at.getY() + i * 24));
      const before = t.deaths(8, 37);
      yield t.key('Q');
      yield t.until(() => t.deaths(8, 37) > before, 120);
      t.expect(t.text()).toContain('스킬');
      t.view(at.getX(), at.getY());
      t.shot('after_q');
  }
  ```
- Input reaches the map as a player's would: the key state table and MSQC flags (KeyDown, MouseDown, val) see it. MSQC results arrive about 3 frames after the input, so wait a few frames (or `t.until`) before a check that depends on them.
- epScript variables have no fixed address, so a test reads what the map already exposes: message lines (the most useful check for text-interface maps), death counters the code keeps, known EUD addresses, the unit count and what the game API reads (unit HP, resources, units of a type). Do not add triggers to the map only for a test. Check the effect itself, not only the message that announces it: for a skill that damages or kills, expect the unit count, a death counter, the targets' HP or a known memory value to change; a message proves only that the message ran.
- A shot shows the 640x480 game screen with the console: terrain, units, sprites and effects, the message lines, the minimap, and for a unit selected with a left click its wireframe, portrait and command buttons. The first four shots of a call come back as one image, two per row, named in order by `imageShots`; every shot is also saved under `build/test/shots/<test>/<NAME>.png`. When you change what a player sees (an effect, a unit that appears, a message's place, a wireframe or button set), shoot it. After every call that returns shots, go through each picture and list what a player would see there (units and buildings, text, effects, the console) before reading the checks; then compare that list with what the request means the player to see. Anything visible that you did not intend (a stray unit or building, debug or warning text, something in the wrong place, something missing) is a problem of this turn even when every check passed: fix it and shoot again, or, when it is an emulator gap or truly not this map's doing, say so in [completion] with the reason. A shot is evidence only for what it shows: when the subject of the check (the hero, the targets, the effect) is not in the picture, the picture verified nothing; aim the view at it (`t.view(X, Y)` at its map pixel position) and shoot again, and never report a visual check as done from a picture that does not show it. A feature the player should see happen (a skill, an attack, a spawn) needs something visible on screen; when the code only changes numbers and prints text, say so as a gap and add a visible effect or ask. A shot with `error` could not be drawn (no graphics driver): rely on the checks and tell the user.
- Results per file: `passed`; `failed` with each check's `actual` value and frame (also when `t.require` or `t.until` failed, when a hook threw: `scriptErrors`, details in `jsLog`, and when the run ended before `test` returned: `stoppedAt` names the step it waited at); `noTest: true` means the file has no top-level `function* test(t)` and only its hooks ran, so it checked nothing; `inconclusive` when the emulator stopped on an unsupported technique; `error` with the test's `problems` (line, code, usage: a syntax error, a frame step not yielded) or `error` (the exception and its file:line) to correct. A failed check can be the test's mistake: check the expectation against the source before changing the map.
- `trace: true` builds a debug variant in build/test/ and reports the epScript line (`where`, `trace`) running at a failure or hang. `profile: true` does the same and counts trigger actions per frame and per epScript line (`top`, `topFunctions`): use it when the user asks about lag or load, compare lines with each other, and treat the numbers as relative (the debug build's trace triggers add work). No count is a lag threshold. `frames: N` plays N frames without tests.
- Passing tests show what the emulator did, not that the real game does the same. In [completion], name what the tests covered and still give the user the in-game checks for the rest.
