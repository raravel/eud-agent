## Map construction

Use the agreed map design and the normal Map Agent handoff. This is a game-space design brief, not a fixed four-player template. For an existing project, repair or extend the accepted layout rather than rebuilding it on every turn.

1. **Translate references into gameplay.** Identify the playable surface, enemy route, defender area, summon/management area, optional boss space, and visual boundaries. A screenshot establishes appearance, not tile passability, elevation, unit collision, or location coordinates. Reuse verified map data when available; otherwise validate those properties on the constructed map. Do not require a reference map or hardcode a particular game's layout.
2. **Keep each arena compact.** Unless the user explicitly requests another scale, make defender placement roughly one gameplay screen, with the enemy route only modestly extending that footprint. The standard per-player scale is approximately a 12 × 12-tile defender bounding box, an 18 × 18-tile combat footprint including the surrounding enemy route, and 20 × 20 tiles including its outer border (one tile = 32 map pixels). These are bounding dimensions, not a required square shape or a promise that every enclosed tile is usable. Summon belongs inside the central placement area. Distinguish summon/management functions through selections, floor patterns or controls within the board; functional distinction does not require an external terrain platform. Budget extra shared facilities only when the accepted mechanics need them. Fit unit capacity, enemy/boss clearances, and attack coverage within this scale; if a requested mechanic cannot fit, surface the tradeoff instead of silently making a larger arena. Fit the accepted player count into the overall map bounds with appropriate gaps and transitions. Do not use map dimensions, gaps between player slots, editor zoom, or the entire slot allocation as the combat footprint. More players increase the number of arenas, not the size of each one.
3. **Make the combat geometry work.** For a loop, define the spawn/join point, ordered turns, direction, and lap/leak condition. Keep the terrain route closed around the defender area: verify every consecutive waypoint segment and the last-to-first segment at the largest supported enemy collision size. The closing segment must follow the intended perimeter, not retrace earlier segments or cross the central board. An open spawn-to-exit path does not satisfy a closed-loop requirement, whatever the arena outline. Spawn enemies directly on the route; process one-lap leaks through tracked waypoint/lap progress rather than cutting a terrain exit. For a lane or branching route, preserve the agreed exits and branch behavior instead. Ensure enemies have no ground path into Summon, placement or management areas. Check that the intended defenders can attack the route at their actual ranges, elevations, and target types. In particular, a defender at the leftmost legal placement must hit enemies entering from the left; moving it two placement cells inward must still reach that entry segment. Record actual placement-cell dimensions and measure this gap in map pixels; do not assume a cell is one tile. Check weapon maximum/minimum range, unit acquisition/seek range, shared weapon users, turret/subunit weapons, ground/air targets, and any range upgrades. Increase the applicable range or repair the geometry according to the accepted roles; a nominal range number alone does not prove automatic targeting. Apply equivalent edge/corner checks to other sides and copied arenas. Reserve boss space only when bosses are agreed. Save route and gameplay regions as named target selections whose exact geometry matches the constructed terrain. Bind spawn points, ordered route waypoints, placement rows/cells, arena boundaries, management zones and leak checks to verified coordinate/mask data; do not create a permanent location for each one. When a consuming API needs locations, use the shared project-owned pool and size it for simultaneous source/destination and nested uses. Document the reason for any dedicated location.
4. **Compose finished terrain tile by tile.** The finished arena needs deliberate MTXM tile composition, not an ISOM brush outline dressed with a few doodads. State this quality requirement explicitly in the Map Agent brief; ISOM may establish rough ground where useful, but its generated silhouette is not the finished design. Build a coherent tileset-specific vocabulary for floor patterns, straight borders, inner/outer corners, junctions, entrances, and transitions. Inspect actual catalog tiles and their rendered combinations before using them; do not guess tile IDs or treat every tile variant as interchangeable. Match neighboring pieces and align repeating patterns so borders terminate cleanly, corners join, and floor motifs do not break at region seams. Distinguish the combat surface, enemy route, and management area through intentional tile patterns, with decoration supporting that structure rather than hiding unfinished edges. Use exact tile arrays or verified region stamps for the designed surface. When an authorized reference map is available, inspect and reuse its actual tile composition as appropriate; a screenshot alone cannot supply exact tile IDs or prove walkability.
5. **Finish one arena before expanding.** Construct and inspect one representative arena for geometry, exact tile composition, saved selections, justified locations, and clearances before creating the rest. Review it both at whole-arena scale and close enough to inspect tile seams. Repair mismatched borders, cut-off patterns, and brush-generated roughness before replication. Use the accepted region's exact tile arrangement as the basis for subsequent arenas, not a fresh series of approximate brush strokes. Preserve equal functional space, route length, attack coverage, and control access when fairness requires them; cosmetic variation must not change difficulty. After copying or translating a region, verify each destination's owner assignments, translated selection geometry, runtime coordinate/mask data, route order, and player bindings. Reuse the runtime pool across sequential player processing rather than copying pool slots per arena; verify distinct IDs/names only for justified dedicated locations. Do not assume copied metadata was remapped correctly. Shared arenas instead need checks for shared targeting, rewards, and management access.
6. **Review the playable map, then bind scripts.** Inspect the whole map and a close view of an arena with location/grid overlays hidden, as well as with gameplay regions visible. Check tile joins, corner orientation, border thickness, pattern alignment, transitions, accidental void or isolated tiles, blocked turns, overlapping management regions, and excessive empty space or visual clutter relative to the agreed style. Read back applied terrain, regions, and objects before wiring their identities into scripts. Exact tile placement still needs passability, elevation, and unit-clearance checks; visual quality alone does not establish those properties. Report artifact checks separately from a live test of representative defenders, a crowded wave, the largest agreed boss, and each supported player count. If the result is only a terrain skeleton or a visually plausible route, describe it as unfinished and continue the agreed work.

Carry the central-summon and closed-loop requirements into the design spec and Map Agent goal. For example: "중앙 배치 구역 안에서 수비대를 직접 소환하고, 바깥 적 경로는 중앙을 둘러싼 끊김 없는 폐쇄 순환로로 유지하세요. 외부 소환장이나 진입 통로를 추가하지 마세요. 마지막 waypoint에서 첫 waypoint까지의 외곽 연결과 중앙/소환 구역으로의 지상 통행 차단을 각각 검증하세요." ## Implement timing, speed, and upgrades

- **One round clock:** keep authoritative phase, round number, and deadline/remaining time in synchronized state. Display round and remaining time at the top throughout preparation/combat, refresh without scrolling chat, reset at each actual phase transition, and handle expiry exactly once. The native countdown uses game seconds (16 simulation frames per second); `getgametick` counts frames. Neither means wall-clock seconds at every speed. Specify the chosen clock and convert deliberately; do not decrement once per arbitrary trigger invocation, stack timers, or repeatedly reset the native countdown while a round is active. Keep spawn intervals, bosses, rewards, and transitions consistent with that clock.
- **EUD turbo:** inspect `plugins_list` and enable/retain `eudTurbo` through the supported project plugin tools, then check the generated build configuration and hook ordering. Do not edit generated EDS as canonical state or add duplicate turbo implementations. Turbo makes triggers run each frame; it is not 2x/3x/4x game speed. Inspect existing waits and cadence-dependent counters when enabling it so draws, spawns, or upgrades do not execute repeatedly.
- **Host speed:** expose clearly labeled 2x, 3x, and 4x controls and show the active multiplier persistently. Establish the authority from verified host information; never assume P1 or the lowest human slot is the lobby host. If host detection is unavailable, resolve a designated-controller policy with the user and label it accurately. Validate requester and allowed values in synchronized logic. Use an existing synchronized command, or verified MSQC input when controls read local keys/mouse; raw local input must not directly change shared speed state. Apply the accepted speed to every client using a verified SC:R-compatible technique. The cited menu is an example, not a built-in `SetGameSpeed` API. Define the baseline and account for integer frame-interval rounding when checking 3x/4x. Do not simulate only faster wave spawning or multiple EPS calls and claim the whole game accelerated. Avoid multiplying the round clock again when engine frames already accelerate. Debounce held inputs, clear consumed requests, reject non-host attempts, and implement the agreed departure policy.
- **Real upgrades:** implement accessible controls, cost/level feedback, insufficient-funds and maximum-level handling, and a single synchronized purchase that charges once. Verify that affected defenders actually gain the specified combat benefit, including future draws. For native weapon upgrades verify upgrade id, damage increment, maximum level, requirements, and usable buttons; for custom levels implement the combat calculation, not only a label. Keep per-player levels independent. Shared DAT/weapon tables cannot implement an isolated player's upgrade by globally increasing every user's weapon damage. Read back all affected DAT/TBL/button changes and preserve unrelated units, especially enemies using the same weapon.

## Text, rarity, selection, and draw feedback

### Assign each message a channel and lifetime

Create a text plan before coding. Specify audience, channel/line allocation, refresh or expiry, maximum encoded length, and source of values. Resolve overlapping output through one HUD composition owner rather than letting gameplay modules overwrite each other's lines.

| Channel | Content and behavior |
| --- | --- |
| Persistent upper HUD | Round/phase, countdown, speed, essential economy/lives/enemy count and upgrade summary. Use verified fixed-line `StringBuffer`/`printAt` techniques or the appropriate native timer, continuously refreshed without flicker or chat spam. |
| Selection panel / reserved HUD lines | Selected defender name, rarity, role/weapon, upgrade and kill information; show `같은 등급 보유: N` for the viewing player's live defenders. Keep visible while selected, update counts/state, clear on deselection, death or replacement. |
| Temporary notification / chat-style output | Draw result, purchase/fusion result, boss/round transition and victory/defeat. Emit once per event, expire predictably, and reserve space so HUD refresh does not erase it immediately. Actual player chat must remain usable. |
| Error line | Short actionable failure such as insufficient currency, full board or invalid fusion. Use a source-verified error-print path with a bounded lifetime and repeated-input throttling. Persistent state belongs in the HUD. |

**Error printing requires synchronization review.** Inspect the installed implementation of `eprintf`/`eprintln`/`eprintAll`, not merely its name. The upstream error-print implementation invokes a CCMU helper that temporarily manipulates the unit free-list and issues a CreateUnit action. Thus a visually local message can invoke synchronized operations.
